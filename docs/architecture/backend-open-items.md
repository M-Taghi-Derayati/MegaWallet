## ۱. `POST /api/v1/swap/prepare` — قرارداد با کلاینت نمی‌خواند

### چه شد

```
--> POST /api/v1/swap/prepare
{"amountRaw":"3000000000000000","fromNetwork":"bsc_mainnet","fromToken":"BNB-BSC",
 "provider":"LI.FI","slippage":0.5,"toAddress":"0xd07f…369c","toNetwork":"base_mainnet",
 "toToken":"0x8335…2913","userAddress":"0xbcd7…88a2"}

<-- 400
{"ok":false,"error":{"code":"SWAP_VALIDATION_ERROR","message":"selectedRoute is required"}}
```

### تشخیص — این یکی **سمتِ ما**ست

`prepare` فقط پنج چیز از بدنه می‌خواند:

```js
swapHub.prepare({
    selectedRoute, userAddress, toAddress, idempotencyKey, currentAllowanceRaw
});
```

تمامِ آنچه کلاینت امروز می‌فرستد — `fromNetwork`، `toNetwork`، `fromToken`، `toToken`،
`amountRaw`، `slippage`، `provider` — خوانده نمی‌شود. مدلِ درخواستِ ما (`SwapPrepareRequestDto`)
برای شکلِ دیگری از قرارداد نوشته شده بود: فرض کرده بود `prepare` خودش دوباره استعلام می‌گیرد.

قراردادِ واقعی این است: `/quote` مسیرها را می‌دهد ← کاربر یکی را انتخاب می‌کند ← کلاینت **همان
شیءِ مسیر را پس می‌فرستد**. با این وصف مسیرِ سواپ در اپ هرگز از مرحلهٔ استعلام جلوتر نرفته است.

### ⚠️ ولی یک شکافِ واقعی هم هست که **سمتِ شماست** — و از خطای ۴۰۰ خطرناک‌تر

`prepare` توکنِ مبدأ را از `selectedRoute.fromToken` می‌خواند:

```js
const fromRef = selectedRoute.fromToken
    ? (selectedRoute.fromToken.id || selectedRoute.fromToken.contractAddress)
    : null;
```

اما `/quote` این فیلد را در **`response.request.fromToken`** می‌گذارد — بالای پاسخ، نه داخلِ
تک‌تکِ `routes[]`:

```js
const dto = {
    request: { fromNetwork, toNetwork, fromToken: this._publicAsset(...), … },
    routes,          // ← آیا هر عضو خودش fromToken دارد؟
    bestRoute: routes[0] || null,
    …
};
```

اگر `routes[i]` خودش `fromToken` نداشته باشد، هر کلاینتی که مسیر را **عیناً** پس بفرستد باعث
می‌شود `fromRef = null` شود، و طبق کامنتِ خودتان در همان فایل:

> توکن را بومی می‌پندارد و approve را رد می‌کند — سواپ روی زنجیره به‌خاطر نبودِ allowance
> برمی‌گردد.

یعنی ۴۰۰ نمی‌گیریم؛ یک باندلِ ناقص می‌سازیم و کارمزد روی زنجیره می‌سوزد. **خطای ۴۰۰ بسیار
بهتر از این است.**

### سؤال‌ها

۱. **شیءِ مسیر را عیناً برگردانیم یا زیرمجموعه‌ای؟**
   کلِ آبجکتِ `routes[i]` بی‌کم‌وکاست، یا فهرستِ مشخصی از فیلدها؟ این تعیین می‌کند JSON خام نگه
   داریم یا از مدلِ تایپ‌دار بازسازی کنیم. اگر verbatim لازم است بگویید — مدلِ فعلیِ ما فیلدهای
   ناشناخته را دور می‌ریزد.

۲. **`selectedRoute.fromToken` از کجا بیاید؟**
   هر `routes[i]` خودش دارد و ما جا انداخته‌ایم، یا واقعاً فقط در `request.fromToken` است؟ اگر
   دومی: ما آن را روی مسیر بچسبانیم، یا شما به هر route اضافه می‌کنید؟ **ترجیحِ ما دومی است.**
   و در هر حال، نبودنش بهتر است `SWAP_VALIDATION_ERROR` بدهد تا اینکه approve بی‌صدا رد شود.

۳. **`currentAllowanceRaw` را نفرستیم چه می‌شود؟**
   سرور خودش allowance را از زنجیره می‌خواند، یا وقتی نباشد همیشه یک لگِ approve می‌گذارد؟ اگر
   انتظار دارید کلاینت بخواند و بفرستد، بگویید.

۴. **`toAddress` در prepare اجباری است؟**
   خودِ مسیر `toAddress` دارد. در `quote` نوشته‌اید وقتی دو زنجیره قالبِ آدرسِ متفاوت دارند
   (ترون base58 ↔ EVM hex) اجباری است. در prepare هم همین است، یا `toAddress`ِ خودِ مسیر کافی
   است؟ اگر کافی است ترجیح می‌دهیم اصلاً نفرستیم تا احتمالِ ناهم‌خوانی صفر شود.

۵. **انقضای استعلام.**
   مسیرها `expiresAt`/`ttlMs` دارند. `prepare` روی مسیرِ منقضی چه کدی می‌دهد؟ ما `QUOTE_EXPIRED`
   و `PREPARE_TOKEN_EXPIRED` را به «دوباره استعلام بگیر» نگاشت کرده‌ایم — تأیید می‌کنید؟

۶. **Idempotency.**
   درخواستِ تکراری `{...prior, idempotent: true}` با `ok:true` برمی‌گرداند. تأیید می‌کنید که
   کلاینت باید این را موفقیتِ عادی بداند و **همان باندلِ قبلی** را امضا کند؟ هدرِ ما
   `x-idempotency-key` با حروفِ کوچک است.

۷. **پل (cross-chain).**
   موردِ شکست‌خورده BSC→Base بود. prepare برای پل چیزی بیشتر از سواپِ هم‌زنجیره لازم دارد؟

## ۲. `/api/auth/challenge` و `/api/auth/device-challenge` — دو بار Gateway Timeout

### چه شد

```
18:14:17.581  --> POST /api/auth/challenge
18:14:32.629  <-- 504  (15047ms)          ← ArvanCloud، server-timing: total;dur=15021
18:14:32.689  --> POST /api/auth/challenge   (تلاش دوباره)
18:14:32.992  <-- 200  (302ms)            ← همان درخواست، ۵۰ برابر سریع‌تر

18:14:33.037  --> POST /api/auth/device-challenge
18:14:48.074  <-- 504  (15036ms)
18:14:48.100  --> POST /api/auth/verify
18:14:48.427  <-- 200  (325ms)
```

### تشخیص — **سمتِ شما**

پاسخِ ۵۰۴ از ArvanCloud می‌آید با `server-timing: total;dur=15021`؛ یعنی مبدأ در پنجرهٔ ۱۵
ثانیه‌ایِ CDN جواب نداد. بلافاصله بعدش همان درخواست ۳۰۲ میلی‌ثانیه طول کشید.

الگویش «کندیِ عمومی» نیست؛ **اولین** درخواست هنگ می‌کند و بعدی‌ها سریع‌اند — شبیهِ راه‌اندازیِ
تنبل، اتصالِ سردِ دیتابیس، یا یک قفل روی مسیرِ challenge.

**هزینه‌اش برای کاربر ۳۱ ثانیه است**: از ۱۸:۱۴:۱۷ تا ۱۸:۱۴:۴۸ فقط صرفِ احراز هویت شد، و در
تمامِ این مدت اپ روی صفحهٔ ورود منتظر می‌ماند.

⚠️ نکتهٔ دوم: بدنهٔ ۵۰۴ یک صفحهٔ HTML ده کیلوبایتی است، نه JSON. برای مسیرهای API بهتر است CDN
یا خودِ اپلیکیشن یک بدنهٔ JSON با همان پوششِ `{ok:false,error:{code,…}}` برگرداند تا کلاینت
بتواند تشخیصِ درست بدهد.

### سمتِ ما — بررسی شد و مشکلی ندارد

- `/challenge` خودکار تلاشِ دوباره می‌کند (و موفق شد).
- شکستِ `/device-challenge` عمداً **نرم** است: attestation نال می‌شود و به مسیرِ verifyِ
  بدونِ دستگاه برمی‌گردیم، پس ورود همیشه کار می‌کند. فقط قابلیت‌های وابسته به دستگاه
  (اعتبارِ گس، جعبهٔ شانس) در آن نشست از دست می‌روند.

پس این یکی اصلاحِ کلاینتی نمی‌خواهد؛ فقط مبدأ نباید ۱۵ ثانیه هنگ کند.

## ۳. Linea — آدرسِ اکسپلوررِ اشتباه در باندلِ تنظیمات

### چه شد

```
--> GET https://api.lineascan.build/api/v2/addresses/0xd07f…369c/transactions
--> GET https://api.lineascan.build/api/v2/addresses/0xd07f…369c/token-transfers
<-- 404   (هر دو)
```

بقیهٔ زنجیره‌ها در همان لحظه ۲۰۰ گرفتند (`eth.blockscout.com`، `arbitrum.blockscout.com`،
`optimism.blockscout.com`، `scroll.blockscout.com`، `polygon.blockscout.com`).

### تشخیص — **سمتِ شما** (یک خط در باندل)

کلاینت برای تاریخچهٔ EVM فقط **Blockscout v2** صحبت می‌کند:

```kotlin
@GET("api/v2/addresses/{address}/transactions")
@GET("api/v2/addresses/{address}/token-transfers")
```

`api.lineascan.build` از خانوادهٔ **Etherscan** است و این مسیرها را ندارد، پس ۴۰۴ می‌دهد.
نمونهٔ Blockscoutِ Linea روی `explorer.linea.build` است.

Linea در `networks.json`ِ همراهِ اپ نیست (آن فایل ۲۲ شبکه دارد و Linea جزوشان نیست)، پس این
آدرس از **باندلِ تنظیماتِ سرور** می‌آید. لطفاً `explorers` برای Linea را به نمونهٔ Blockscout
عوض کنید.

⚠️ اثرش خاموش است: تاریخچهٔ Linea همیشه خالی برمی‌گردد و هیچ خطایی به کاربر نشان داده نمی‌شود.

### یک نکتهٔ مرتبط برای خودمان (سمتِ ما)

در همان تنظیمات فیلدی به نامِ `explorerApi` هست (مقدارش برای همه `"etherscan"`) که کلاینت
**اصلاً نمی‌خواندش** و همیشه Blockscout فرض می‌کند. یعنی امروز اعلامِ خانوادهٔ اکسپلورر در
تنظیمات بی‌اثر است. تا وقتی همهٔ شبکه‌ها Blockscout باشند مشکلی پیش نمی‌آید، ولی اگر قرار است
شبکه‌ای با API خانوادهٔ Etherscan اضافه شود، اول باید کلاینت آن را پشتیبانی کند. لطفاً پیش از
افزودنِ چنین شبکه‌ای به ما خبر دهید.
